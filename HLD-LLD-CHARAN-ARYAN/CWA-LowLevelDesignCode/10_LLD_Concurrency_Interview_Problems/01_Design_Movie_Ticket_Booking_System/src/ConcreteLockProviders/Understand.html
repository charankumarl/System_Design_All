1. The Three Requests

Same show. Three different customers call lockSeats() at roughly the same moment.

U1
[1, 2]
U2
[2, 3]
U3
[2, 4]
Seats 1, 3, 4 are each wanted by only one user — no real conflict there. Seat 2 is the only point every request overlaps on — that's the entire fight.

2. Each Request Sorts Its Own Seats First

U1 → sorted [1, 2]
U2 → sorted [2, 3]
U3 → sorted [2, 4]
This matters later: every thread locks its lowest seat ID first. Nobody ever holds a high seat and reaches backward for a lower one — that's exactly what prevents a deadlock here.

3. The Race for Seat 2's ReentrantLock

All three threads eventually call seatLockMap.computeIfAbsent(seat2,...).lock(). Only one can hold it — the OS thread scheduler decides who gets there first, which is genuinely non-deterministic. For this walkthrough, say U2 wins.

winner — proceeds blocked, waiting uncontested, acquired instantly
U1→holds seat 1's lock (nobody else wanted it) · now blocked waiting for seat 2
U2→WINS seat 2's lock · proceeds to seat 3 (uncontested, instant)
U3→blocked, waiting for seat 2

Right now: U2 is running. U1 and U3 are both parked, queued on seat 2's lock.

4. U2 Runs Its Check + Write, Fully Unopposed winner

check seat2 → no entry → free
check seat3 → no entry → free
→ writes SeatLock(U2) for seat 2
→ writes SeatLock(U2) for seat 3
finally → releases seat2's lock, releases seat3's lock
Seat 2→SeatLock(U2) — written
Seat 3→SeatLock(U2) — written
U2's booking succeeds completely. Seat 2's ReentrantLock is now free again — the next waiter can proceed.

5. Seat 2 Frees Up — Say U3 Gets It Next loser

U3 acquires seat2's lock → also grabs seat4's lock (uncontested)

check seat2 → SeatLock(U2) found, NOT expired
→ throw "Seat 2 is already locked"

finally → releases seat2's lock AND seat4's lock
Seat 2→U3 wanted it — blocked by U2's entry
Seat 4→U3 loses this too, even though nobody else wanted it
U3's entire request fails — including seat 4, which was never actually contested. It's all-or-nothing: a request either gets every seat it asked for, or none of them.

6. Last One Standing: U1 loser

U1 was parked on seat 2's lock this whole time, still holding seat 1's lock from the very start. Once U3 releases seat 2, U1 finally gets it.

check seat1 → no entry → free
check seat2 → SeatLock(U2) found, NOT expired
→ throw "Seat 2 is already locked"

finally → releases seat1's lock AND seat2's lock
Seat 1→U1 held this uncontested the whole time — loses it anyway
Seat 2→blocked by U2's entry
U1's entire request also fails. Same all-or-nothing rule — holding seat 1 the whole time counted for nothing once seat 2 turned out to be taken.

7. Final Outcome

UserWantedResult
U11, 2❌ Fails entirely — loses seat 1 too
U22, 3✅ Succeeds — gets both seats
U32, 4❌ Fails entirely — loses seat 4 too

8. Key Takeaways

1. Exactly one of the three wins — whichever thread gets seat 2's lock first and completes its check+write before the others reach their own check.
2. Who wins is non-deterministic — depends on OS thread scheduling, not the code. Running this 100 times could produce U1, U2, or U3 winning in different runs.
3. Losing is all-or-nothing — a loser's entire request fails, even seats nobody else wanted (seat 1 for U1, seat 4 for U3). You never end up with half your requested seats.
4. No deadlock — every thread locks seats in ascending ID order, so nobody ever ends up in a circular "I'm waiting for what you're holding, you're waiting for what I'm holding" situation.
